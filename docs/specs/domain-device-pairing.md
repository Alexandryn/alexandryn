## Context

Phase 13 opens the host beyond loopback. A device that is not the desktop
host — a phone, a tablet, a TV browser — needs a way to reach the library
that does not require typing a bare IP address and a full credential on a
poor keyboard. ADR 0028 §6 fixes the model: the device still authenticates
with a phase-12 account (ADR 0025 unchanged), and **pairing** is a thin
bootstrap that proves "the host operator intends this device" and carries
the host address to it. This spec defines the pure domain types that model
that bootstrap and their invariants. It has no networking, no crypto, and
no persistence — those live in `backend-network-transport.md` and
`backend-network-api.md`.

## Problem

There is no domain model for a pairing handshake: no representation of a
pending pairing, the one-time code that authorises it, the state it moves
through, or the record left behind when a device completes it. Without
one, the pairing endpoints in `backend-network-api.md` would carry the
state machine and its invariants inline in HTTP handlers, where they
cannot be unit-tested in isolation and where an illegal transition
(reusing a consumed code, verifying an expired session) becomes a bug
rather than a rejected move.

## Goals

- A `PairingSession` aggregate that owns the full lifecycle of one
  pairing attempt and rejects every illegal transition as a typed error.
- A `PairingCode` value object with a fixed format and length, and
  constant-time comparison as its only comparison path (the entropy floor
  lives with the generator in `backend-network-transport.md` FR-9).
- A `PairedDevice` entity recording a completed enrolment, owned by the
  user who signed in on the device (never the admin who initiated the
  pairing), carrying no device fingerprint beyond a coarse class.
- Time handled through an injected clock so every TTL and expiry rule is
  deterministically testable (`architecture-testing.md` FR-6).
- Zero imports of `net`, `crypto/*`, `database/sql`, `pgx`, or any
  transport package. Random bytes are generated by a caller in an adapter
  and handed in.

## Non-goals

- Generating the random bytes for a code. The domain validates and
  compares; an adapter in `backend-network-transport.md` generates
  (`crypto/rand`) and encodes.
- Persisting any of these types. `backend-network-api.md` owns the
  `pairing_sessions` and `paired_devices` tables and their repositories.
- The standing device inventory — listing every paired device, renaming
  one, per-device session-expiry policy, cross-device reading-progress
  sync. That is **phase 14** (`14-devices-and-sync`). This spec models
  *pairing a device* and *revoking a pairing you just made*; it does not
  model device management as an ongoing surface (ADR 0028 §6, plan C-3).
- The enrolment grant's token format and signing. It is a short-lived
  artefact minted and verified in `internal/auth` alongside the JWT
  signer; this spec only names that `pair/verify` produces one.
- Any relationship to TOTP MFA (ADR 0027). Pairing precedes login;
  whatever MFA the account requires happens in the phase-12 login flow the
  device runs after enrolment.

## User stories

- As **the pairing HTTP handlers** (`backend-network-api.md`), I want one
  aggregate whose methods are the only legal ways to advance a pairing, so
  an illegal move is a returned error, not something I have to remember to
  guard against.
- As **a test author**, I want every TTL and single-use rule to depend on
  an injected clock and an injected code value, so I can assert
  "expires exactly at T+5m" and "a second verify fails" without sleeping
  or touching a random source.
- As **phase 14's device inventory**, I want a `PairedDevice` record with
  a stable identity, an owning user, and enough metadata to show a useful
  list, but no covert fingerprint I would then have to justify storing.

## Functional requirements

Numbered, testable, RFC 2119.

- **FR-1** A `PairingCode` MUST be a value object wrapping a string in a
  fixed format: base32 (Crockford alphabet, no padding, uppercase),
  regrouped for display as two groups of four characters separated by a
  hyphen (`XXXX-XXXX`). Construction from an untrusted string MUST reject
  (typed error) any value that is not exactly this shape after
  case-folding and hyphen-stripping. The domain MUST NOT expose any
  equality path other than `Equal(other PairingCode) bool` implemented
  with `crypto/subtle.ConstantTimeCompare` over the normalized bytes — no
  `==`, no `strings.EqualFold`, no map keying on the raw value.
- **FR-2** The `PairingCode` constructor MUST enforce a fixed **shape and
  length**: exactly eight Crockford-base32 characters (after case-folding
  and stripping the display hyphen), each in the Crockford alphabet
  (`0-9A-HJKMNP-TV-Z`, excluding `I`, `L`, `O`, `U`). It rejects seven
  characters, nine characters, a non-Crockford character, base32 padding
  (`=`), and whitespace. A constructor over an untrusted string can check
  shape but **not** entropy — entropy is a property of how the value was
  *generated*, not of the string. The ≥ 40-bit entropy requirement
  therefore lives in `backend-network-transport.md` FR-9
  (`GeneratePairingCode` reads 5 bytes = 40 bits from `crypto/rand`); its
  acceptance criteria assert it, not this spec's. Eight Crockford
  characters is the smallest fixed format that can *carry* 40 bits, which
  is why the shape check is set here. The ≤ 5-minute TTL (FR-3) and the
  per-IP rate limit (`backend-network-transport.md` FR-8) are what make 40
  bits sufficient against online guessing.
- **FR-3** A `PairingSession` MUST be an aggregate with:
  - an identity (`PairingSessionID`, an opaque string — a UUID in
    practice, treated as unguessable per the same convention `domain/id.go`
    already uses),
  - the `UserID` of the admin who initiated it,
  - its `PairingCode`,
  - a `PairingState` (FR-4),
  - a `CreatedAt` and an `ExpiresAt` where
    `ExpiresAt == CreatedAt.Add(ttl)` and `ttl` is a construction
    parameter that MUST be `> 0` and MUST be `<= 5 * time.Minute` (a
    caller passing more is a programming error and construction returns an
    error, not a silently clamped value),
  - an optional `DeviceID`, nil until FR-6 sets it.
  The `PairingCode` on a rehydrated session comes from
  `backend-network-api.md` decrypting the stored ciphertext (ADR 0028 §6 —
  codes are stored AES-256-GCM-encrypted, not hashed, precisely so the
  value object can be reconstructed here and FR-6's own constant-time
  compare still runs). The domain neither encrypts nor decrypts; it
  receives a validated `PairingCode` either way.
- **FR-4** `PairingState` MUST be exactly one of `pending`, `verified`,
  `consumed`, `expired`, and the only legal transitions are:
  - `pending → verified` — via `Verify` (FR-6),
  - `verified → consumed` — via `Consume` (FR-7),
  - `pending → expired` and `verified → expired` — via `ExpireAt` (FR-5).
  Every other transition (`consumed → *`, `expired → *`, `pending →
  consumed`, re-running `Verify` on a non-`pending` session) MUST return a
  typed error naming the current state and the attempted move, and MUST
  NOT mutate the aggregate. `consumed` and `expired` are terminal.
  (An earlier draft included a `claimed` state between `pending` and
  `verified` for a "code entered, awaiting confirmation" step; removed —
  the design shows no such intermediate confirmation and it added a
  transition with no behaviour attached to it.)
- **FR-5** `ExpireAt(now time.Time)` MUST move a `pending` or `verified`
  session to `expired` when `now` is at or after `ExpiresAt`, and MUST be
  a no-op (no error, no mutation) otherwise or when the session is already
  terminal. Every other method that advances state (`Verify`, `Consume`)
  MUST itself check expiry first against the `now` it is passed and MUST
  return the expiry error (moving the session to `expired`) rather than
  proceeding, so a caller cannot advance a stale session by skipping
  `ExpireAt`.
- **FR-6** `Verify(now time.Time, submitted PairingCode, deviceID
  DeviceID)` MUST, in order: (1) fail with the expiry error if `now >=
  ExpiresAt` (also moving to `expired`); (2) fail with a "wrong state"
  error if the session is not `pending`; (3) compare `submitted` to the
  session's code via FR-1's constant-time `Equal` and fail with a generic
  "code does not match" error on mismatch **without** changing state (a
  wrong guess does not burn the session — the rate limiter bounds guessing,
  and burning on first wrong guess would let an attacker grief a real
  pairing); (4) on match, set `DeviceID = deviceID` and state = `verified`.
  A `DeviceID` of the zero value MUST be rejected at step 4 as a
  programming error.
- **FR-7** `Consume(now time.Time)` MUST fail with the expiry error if
  expired, fail with a "wrong state" error unless the session is
  `verified`, and otherwise move the session to `consumed`. `Consume` is
  the point at which the enrolment grant has been issued to the device;
  after it, the session can never be verified or consumed again. The
  transition from `verified` to `consumed` MUST be expressible as a single
  method call so `backend-network-api.md` can perform it inside the same
  database transaction that writes the `PairedDevice` row (ADR 0021).
- **FR-8** A `PairedDevice` MUST be an entity with: a `DeviceID`
  (opaque, unguessable), the **`Owner` `UserID` — the user who completed
  `POST /api/v1/auth/login` carrying the enrolment grant, NOT the admin
  who initiated the `PairingSession`** (`backend-network-api.md` FR-9;
  ADR 0028 §6 — a device belongs to whoever signs in on it). A `Label` (a
  non-empty string ≤ 100 runes after trimming — supplied by the enrolling
  client or derived by the API layer from the `User-Agent`, validated
  here), a `DeviceClass` enum (`phone`, `tablet`, `desktop`, `tv`,
  `unknown` — a coarse classification the API layer derives from the
  `User-Agent`; the domain stores it, does not parse it), an `EnrolledVia`
  enum, a `CreatedAt`, a `LastSeenAt` (initially equal to `CreatedAt`),
  and a nullable `RevokedAt`.
  - `EnrolledVia` has two values, `pairing_code` and `password_login`.
    **Phase 13 only ever writes `pairing_code`** — it is the only
    enrolment path this phase builds. `password_login` (a device that
    signed in directly, no pairing) is reserved for **phase 14**'s device
    inventory; it is in the enum now only so the persisted column's check
    constraint does not need a migration when phase 14 arrives. A phase-13
    rehydration test still exercises both values (an unknown string is
    rejected), but no phase-13 code path constructs a `password_login`
    device.
- **FR-9** `PairedDevice.Revoke(now time.Time)` MUST set `RevokedAt = now`
  and MUST return a typed error (no mutation) if `RevokedAt` is already
  set — revocation is idempotent in effect but a double-revoke is a
  caller bug worth surfacing. Phase 13's one caller is
  `DELETE /api/v1/network/pair/{id}` (`backend-network-api.md` FR-6 — an
  admin undoing a pairing they just made).
  - `PairedDevice.Touch(now time.Time)` (advance `LastSeenAt` forward
    only, never backward under clock skew; fail if revoked) is **specified
    here but has no phase-13 caller** — nothing in phase 13 records a
    per-device "last seen". It is defined now so phase 14's inventory does
    not have to re-open this spec to add it, and the phase-13 unit tests
    cover it. If the maintainer prefers, `Touch` moves wholesale to
    phase 14's spec; the method's shape does not change either way.
  - A revoked device is inert: phase 14 decides the full consequence
    (session invalidation cascade — see Open questions), but this spec
    fixes that a revoked `PairedDevice` accepts no further state change
    except staying revoked.
- **FR-10** No type in this spec MUST store, derive, or accept: an IP
  address, a full `User-Agent` string, a screen resolution, a hardware
  identifier, a MAC address, or any value whose purpose is to
  re-identify a device across enrolments. `DeviceClass` is the only
  device-descriptive field and it is deliberately coarse. (The
  `pairing_sessions` / `paired_devices` *tables* in
  `backend-network-api.md` may store an IP for an operator's own
  audit view — that is a persistence-layer decision bounded by
  constitution §8's "never log … home-directory paths … or what someone
  is reading"; it does not enter these domain types.)

## Non-functional requirements

- **Performance** — not applicable; these are in-memory value operations
  on the request path, no measurable budget.
- **Security** — see Security considerations. The constant-time
  comparison (FR-1) and the no-burn-on-wrong-guess rule (FR-6) are the
  two security-load-bearing decisions in the pure domain; everything else
  protective (entropy source, rate limiting, TTL enforcement at the
  socket) is in `backend-network-transport.md`.
- **Accessibility** — not applicable; no UI.
- **Reliability** — the aggregate has no persistence of its own; on a
  restart, an in-flight `PairingSession` is whatever the
  `pairing_sessions` table last held, re-hydrated through a constructor
  that re-validates every invariant (FR-3, FR-4). A row that violates an
  invariant (an `ExpiresAt` more than 5 minutes after `CreatedAt`, an
  unknown state string) MUST fail re-hydration loudly, not load a
  malformed aggregate.
- **Observability** — the domain emits no logs. Callers logging a pairing
  event MUST log the `PairingSessionID` and `DeviceID` and `UserID`, and
  MUST NOT log the `PairingCode` in any form (constitution §8 — the code
  is a short-lived credential-equivalent).

## Domain model

New types, all in the **Alexandryn** domain (`internal/domain`) — a
device a user has paired is "what the user has and does" (constitution
§3), not metadata and not a source. None of them reference metadata or
source types.

| Type | Kind | New/changed |
|---|---|---|
| `PairingSession` | Aggregate root | New |
| `PairingState` | Enum | New |
| `PairingCode` | Value object | New |
| `PairingSessionID` | Identity | New |
| `PairedDevice` | Entity | New |
| `DeviceID` | Identity | New |
| `DeviceClass` | Enum | New |
| `EnrolledVia` | Enum | New |

No existing domain type changes. `UserID` (from `domain/auth.go`) is

violate that spec's own rule).

## API and contracts

This spec defines Go types and methods only. The one cross-boundary
contract:

- **`PairingSession` ↔ its repository** (`backend-network-api.md`): the
  aggregate exposes a rehydration constructor
  (`RehydratePairingSession(...)`) taking every persisted field and
  returning `(*PairingSession, error)`, matching the pattern
  `domain/rehydrate.go` already establishes for other aggregates. The
  repository never constructs a `PairingSession` by struct literal.

No HTTP shapes, no JSON, no wire format here.

## State transitions

`PairingSession`:

```
          Verify(code ok)            Consume
pending ───────────────────► verified ──────────► consumed   (terminal)
   │                             │
   │ ExpireAt / method sees      │ ExpireAt / method sees
   │ now >= ExpiresAt            │ now >= ExpiresAt
   ▼                             ▼
expired ◄─────────────────────────┘                          (terminal)
```

Illegal, each a test:

- `Verify` on `verified`, `consumed`, or `expired` → "wrong state" error.
- `Verify` with a non-matching code → "code does not match", **state
  unchanged** (still `pending`).
- `Consume` on `pending`, `consumed`, or `expired` → error.
- Any method on a terminal session → error or documented no-op
  (`ExpireAt` is the only no-op).
- Construction with `ttl <= 0` or `ttl > 5m` → error.

`PairedDevice`:

```
active ──Revoke──► revoked   (terminal)
  │
  └─Touch (only moves LastSeenAt forward)
```

Illegal: `Touch` on a revoked device → error; second `Revoke` → error.

## Failure modes

| Failure | Detected how | Caller sees | Domain does |
|---|---|---|---|
| Untrusted code string is malformed | `PairingCode` constructor (FR-1) | Typed `ErrInvalidPairingCode` | Returns error, constructs nothing |
| Code is 7 or 9 chars, or has a non-Crockford char / padding / whitespace | Constructor (FR-2) | Same typed error | Same |
| `Verify` with expired session | FR-6 step 1 | `ErrPairingExpired` | Moves session to `expired`, returns error |
| `Verify` with wrong code | FR-6 step 3 | `ErrPairingCodeMismatch` (generic) | **No mutation**; session stays `pending` |
| `Verify` twice (replay) | FR-6 step 2 on second call | `ErrPairingWrongState` | No mutation on the second call |
| `Consume` before `Verify` | FR-7 | `ErrPairingWrongState` | No mutation |
| Rehydrating a row with `ExpiresAt - CreatedAt > 5m` or unknown state | Rehydration constructor (Reliability NFR) | Typed error | Loads nothing |
| `Touch` / second `Revoke` on a revoked device | FR-9 | `ErrDeviceRevoked` / `ErrAlreadyRevoked` | No mutation |
| Empty or over-long `Label` | `PairedDevice` constructor (FR-8) | Typed validation error | Constructs nothing |

## Security considerations

- **Trust boundary** — these types sit behind the HTTP layer. The
  `submitted PairingCode` in `Verify` originates from an untrusted network
  client; it reaches the domain only after `backend-network-transport.md`
  has applied a size limit and the `PairingCode` constructor has enforced
  the shape (FR-1). The domain assumes the *format* is validated by its
  own constructor and assumes nothing else about the value.
- **Timing** — FR-1's constant-time `Equal` is mandatory because a
  non-constant-time compare of a 40-bit secret over a LAN is a realistic
  side channel. This is the one place in the pure domain where a timing
  property is a correctness requirement, not a nicety.
- **No burn on wrong guess (FR-6)** — deliberately, a wrong code does not
  consume the session. Burning on first wrong guess would let any
  unauthenticated LAN client cancel a legitimate pairing by racing one
  bad guess to it. The guessing budget is bounded instead by the rate
  limiter and the 5-minute TTL: at, say, 10 attempts/minute that is ≤ 50
  guesses against a 2^40 space — a ~4×10⁻¹¹ success probability per
  window.
- **TTL ceiling in the type (FR-3)** — the 5-minute maximum is enforced
  at construction, not left to the caller, so a future endpoint cannot
  widen the window by passing a larger `ttl`. Shortening it is allowed.
- **No fingerprinting (FR-10)** — the domain refuses to hold any value
  that would let paired devices be correlated or tracked beyond the
  coarse class needed to render a list. This is a privacy property
  (constitution §8's spirit) baked into the type, so a later contributor
  adding "just an IP for debugging" to `PairedDevice` has to change the
  spec to do it.
- **STRIDE** — *Spoofing*: the code proves operator intent, not identity;
  identity is still the phase-12 login the device runs next.
  *Tampering*: constructors re-validate every field on rehydration.
  *Repudiation*: callers log `PairingSessionID`/`DeviceID`/`UserID`
  (Observability NFR). *Information disclosure*: the code is never logged;
  no fingerprint is stored. *Denial of service*: the no-burn rule
  prevents pairing-cancellation griefing; guess-flooding is the transport
  layer's rate limiter. *Elevation of privilege*: pairing yields an
  enrolment grant, never a session and never a role — the device's
  eventual privileges are exactly the account it logs into.

## Test strategy

| Layer | What it covers |
|---|---|
| Unit | Every FR. `PairingCode` constructor: valid, wrong length, non-Crockford chars, padded, lowercased (accepted after fold), hyphen variations; `Equal` is constant-time (structural — assert it calls `subtle.ConstantTimeCompare`, and a benchmark-style equal-time check is a nice-to-have not a gate). `PairingSession`: full legal path `pending → verified → consumed`; every illegal transition from the State transitions section returns the right typed error with no mutation; `ExpireAt` at `ExpiresAt - 1ns` (no-op), at `ExpiresAt` (expires), at `ExpiresAt + 1h` (expires, idempotent); `Verify`/`Consume` each independently reject a session that is past `ExpiresAt` even if `ExpireAt` was never called; construction rejects `ttl` of `0`, negative, `5m + 1ns`; accepts `5m` exactly and `1s`. `Verify` wrong-code leaves state `pending` and a subsequent correct `Verify` still succeeds. `PairedDevice`: `Touch` moves `LastSeenAt` forward only, never backward; `Revoke` then `Touch` errors; double `Revoke` errors; `Label` trimming and length bounds; `DeviceClass`/`EnrolledVia` unknown-string rejection on rehydration. |
| Integration | None — no I/O in this package. |
| Contract | None — no wire format. |
| E2E | None at this layer. |
| Accessibility | N/A. |

Tests that MUST fail before implementation: the full `PairingSession`
legal-path test, the illegal-transition table test, and the
`PairingCode` constant-time-`Equal` structural test.

## Acceptance criteria

- [ ] `PairingCode` has no equality path except a constant-time `Equal`;
      proven by a test and by `grep` finding no `==` on the wrapped type
      and no `strings.EqualFold` of a code.
- [ ] `PairingCode` construction rejects every malformed shape in the
      test list and accepts exactly the `XXXX-XXXX` Crockford form
      (case-folded).
- [ ] The `PairingCode` constructor accepts exactly the 8-char Crockford
      form (case-folded, hyphen optional) and rejects 7 chars, 9 chars, a
      non-Crockford character, `=` padding, and whitespace — one test per
      case. (The ≥ 40-bit *entropy* assertion lives in
      `backend-network-transport.md` FR-9's acceptance criteria, not here.)
- [ ] `PairingSession` advances only along the four legal transitions;
      every other move returns a typed error naming state + attempt and
      leaves the aggregate unmutated — one test per illegal move.
- [ ] A wrong code in `Verify` returns a generic mismatch error and does
      **not** change state; a later correct `Verify` succeeds.
- [ ] `Verify` and `Consume` each reject a past-`ExpiresAt` session on
      their own, without a prior `ExpireAt` call.
- [ ] Construction rejects `ttl <= 0` and `ttl > 5m`; accepts `5m`.
- [ ] `verified → consumed` is a single method call, usable inside one
      transaction (verified by `backend-network-api.md`'s repository test,
      referenced here).
- [ ] `PairedDevice.Touch` never moves `LastSeenAt` backward; a revoked
      device rejects `Touch` and a second `Revoke`.
- [ ] No type in the package references `net.IP`, `*http.Request`, a raw
      `User-Agent`, or any hardware identifier — proven by an
      import/field audit test.
- [ ] Rehydration re-validates all invariants and fails loudly on a
      malformed persisted row.
- [ ] Every FR maps to a line in phase 13's exit criteria.

## Open questions

- **Should `PairingSession` carry the enrolling device's requested
  `Label` from `pair/verify`, or does `backend-network-api.md` derive the
  label at `Consume` time from the `User-Agent`?** Leaning: the API layer
  derives a default (`"Pixel 8 · Chrome"`-style) and the user renames it
  in phase 14; the session does not carry it. Not fixed here — flagged
  for the `backend-network-api.md` scope review.
- **Does revoking a `PairedDevice` need to invalidate that device's
  outstanding phase-12 refresh tokens immediately?** Almost certainly
  yes, but the mechanism (a `device_id` column on `user_refresh_tokens`,
  a revocation cascade) is a persistence + auth concern that phase 14's
  device-management spec is better placed to design. Phase 13 ships
  `Revoke` as a domain state change; the cascade is phase 14. Recorded so
  it is not assumed done.
- **`DevicePaired` domain event** — deferred to phase 14 per
  `domain-events.md`'s "nothing may emit an event nothing consumes" rule.
  Named here only so phase 14 knows this spec considered and deferred it.
