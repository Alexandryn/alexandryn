# 0010. Bibliographic identity is internal-ID-primary; external references are optional and never required

## Context

Phase 02's own exit criteria requires this as a recorded ADR, separately
from `domain-bibliographic.md` (where the decision was actually made and
implemented as FR-1/FR-2/FR-3/FR-7). Written here to formalize it as its
own record rather than leave it only implicit in a spec's functional
requirements — the roadmap's own bar for what deserves an ADR
(`decisions/README.md`: "expensive to reverse... would otherwise look
arbitrary to someone reading the code later") is squarely met: every
later phase's identifiers, foreign keys, and matching logic depend on
this.

The forcing question: what identifies a `Work`, `Edition`, or `Author` —
an external identifier (Open Library's `OL27448W`-style keys, ISBNs), an
internal one generated by Alexandryn, or both — and critically, what
happens when a book has no external identifier at all, which phase 02's
own risk table insists "must be a first-class case, not an error state,
because imported files often have none."

## Decision

Internal identifiers (generated at creation) are the *only* primary
identity for `Work`, `Edition`, and `Author`. External references (an
Open Library key, an ISBN) are optional, attached fields — present or
absent, never required, never used as a primary or foreign key anywhere
in the domain. A record with zero external references is exactly as
valid, permanent, and first-class as one with several
(`domain-bibliographic.md` FR-3).

Matching two records as "the same" (dedup) is never computed from string
similarity by the domain itself — it's a decision made elsewhere (phase
07's Open Library normalisation, phase 10's import matching) and merely
*recorded* by the domain once made, reversibly
(`domain-bibliographic.md` FR-4/FR-7).

## Options considered

### Option A — Internal ID primary, external references optional and attached (chosen)

*For* — a work with no Open Library match (an imported file with no
metadata, or a book Open Library simply doesn't have) is fully
functional from the moment it's constructed — no placeholder external ID,
no special-cased "unmatched" type. Matching happens whenever it happens,
recorded as an update to existing data, not a precondition for the record
to exist at all.

*Against* — every entity needs its own ID-generation and needs the domain
to carry two identity concepts (internal, external) instead of one — more
type surface than a single-identifier scheme.

### Option B — External identifier (Open Library key) as primary identity

*For* — simpler in the case where a match already exists; no separate
internal ID scheme to design.

*Against* — directly fails phase 02's own named requirement: a book with
no Open Library record would have no identity at all, forcing either an
error state or an invented placeholder ID scheme anyway — which is just
Option A with extra steps and a worse default case. Rejected outright.

### Option C — Composite identity (external ID when present, generated fallback when absent)

*For* — looks like it gets both worlds.

*Against* — two different code paths construct identity depending on
data availability, and anything keying off "the identifier" has to know
which kind it's holding — exactly the kind of implicit special-casing
`domain-bibliographic.md` FR-3 is designed to avoid ("not a different
case to handle downstream"). Rejected: Option A achieves the same outcome
(both worlds available) without the caller ever needing to know which
kind of identity a record has, because there's only ever one kind.

## Consequences

**Good** — no privileged path for "verified" (Open-Library-matched) data
over "unverified" (imported, unmatched) data; both are first-class from
construction. Matching/dedup can happen at any time, including never,
without blocking anything.

**Bad** — every entity carries an internal-ID-generation responsibility
phase 03 has to implement consistently (a ULID/UUID scheme, collision
handling in the vanishingly unlikely case) — a small but real
implementation surface Option B wouldn't have needed.

**Neutral** — doesn't decide the actual ID generation algorithm (UUID v4,
ULID, etc.) — phase 03's implementation detail, not this ADR's.

## Reversal cost

High once phase 03 builds persistence and phase 07/10 build matching
against this scheme — every foreign key, every API response shape
(`architecture-contracts.md`), and every import pipeline would need
migrating. Cheap right now — nothing built yet, this is exactly the point
in the process where the cost of getting it right is lowest.

## Confidence

High. This isn't a judgment call weighed against a close alternative —
Option B provably fails phase 02's own stated requirement (unmatched
books as a first-class case), and Option C achieves nothing Option A
doesn't already achieve more simply. The design prototype's own
`WORK → 12 EDITIONS` hierarchy assumes internal grouping independent of
any specific external catalog too, consistent with this choice.
